# etcd 在 go-zero 里到底干什么

go-zero 的微服务里，调用方通常不写死对方的 IP。etcd 干的就是这件事：把**服务名**映射成**当前还活着的实例地址**。

前端类比：它不是 Redux（那是应用状态），更像一份会自动更新的服务注册表——谁上线、谁挂了，表立刻变。gRPC 客户端这边，go-zero 用装饰器在原有调用外包一层解析/负载均衡，接口不变，只是多了「去 etcd 查地址」这个能力。

## 1. etcd 的本质

etcd 本质是一张动态的 key-value 表：

- **key**：服务名，例如 `user.rpc`
- **value**：该服务当前实例的 `IP:Port` 列表

RPC 进程启动时向 etcd 登记自己；进程挂了，这条登记会被删掉。调用方 watch 这份表，地址变了不用重启去改配置。

## 2. 什么时候才需要

- **单机、地址固定**：yaml 里写死 `127.0.0.1:8080` 即可，etcd 是多余的。
- **多机、同一服务多个实例、IP 会变**：才需要 etcd 当地址簿。

判断标准就一句：调用方能不能在配置里写死对方地址。能写死就不用；不能写死才上 etcd。

## 3. api 和 rpc 为什么成对出现

一个业务模块通常是一对：

- **xxx-api**：对外 HTTP，前端或网关打过来
- **xxx-rpc**：对内 gRPC，给其他服务用

请求链路：

```
前端 → Nginx（统一入口）→ xxx-api（HTTP 转 gRPC）→ xxx-rpc（业务）→ 数据库
```

前端类比：api 层 ≈ BFF。浏览器不直连 gRPC；由 api 鉴权、转协议，再拿 etcd 里的 key（例如 `user.rpc`）去找实例。

api 连 rpc 时配的不是 IP，而是 etcd 的 Hosts + **同一个 Key**。两边 Key 必须一致，否则 api 在表里找不到人。

部署上：开发可以把 api 和 rpc 放同一台机器、不同端口；生产则分开部署，独立扩缩容、故障隔离。

## 4. etcd 自己怎么部署

- 开发：1 个节点够用
- 生产：3 或 5 个节点（**奇数**），组成集群

原因是多数派投票（Quorum）：超过半数节点活着，集群才能读写。2 个节点挂 1 个就失去多数；3 个节点允许挂 1 个。4 个节点仍然只允许挂 1 个，却多一台机器，所以用奇数。

## 5. 配置谁定、谁注入

| 配置项 | 谁定 | 说明 |
|---|---|---|
| `Host: 0.0.0.0` | 开发者 | 监听所有网卡 |
| `Port` / `ListenOn` | 开发者 | 不冲突即可 |
| `Key: user.rpc` | 开发者 | 服务名，api 与 rpc 必须一致 |
| `${ETCD_HOSTS}` | 运维注入 | etcd 地址 |
| `${JWT_SECRET}` | 运维注入 | 密钥，不要写进代码 |

`ETCD_HOSTS` 格式：本地 `127.0.0.1:2379`（2379 是 etcd 默认客户端端口）；生产集群写成逗号分隔，例如 `192.168.0.111:2379,192.168.0.112:2379,192.168.0.113:2379`。

yaml 里的 `${ETCD_HOSTS}` 是**启动时**读进程环境，不是构建时写死。前端类比：不是 webpack 打进包的 `import.meta.env`，而是进程起来后读 `process.env`。

## 6. 记住这一句就够

日常开发：写业务；本地 `.env` 配 `ETCD_HOSTS=127.0.0.1:2379`；Host、Port、Key 定好就别反复改。etcd 集群地址和密钥，留给部署时注入。
